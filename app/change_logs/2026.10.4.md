# 2026.10.4 — 2026-10-25

A follow-up to 2026.10.3's credential gating. The gate's documented escape hatch did not actually work, and its default was wrong for this product shape; both are fixed. No InfluxDB field/tag changes this release.

## Issues Closed

- KASACOLLEC-107 — `KASA_COLLECTOR_TRUST_DISCOVERED_DEVICES=True` (and listing a device in `KASA_COLLECTOR_DEVICE_HOSTS`) did not actually authenticate a discovered SMART/KLAP device; the drop was mislabelled and leaked an aiohttp session.
- KASACOLLEC-108 — the credential gate defaulted ON, so auto-discovery silently dropped the operator's own SMART/KLAP devices on a headless collector with no way to approve them but a manual list. Default reversed.

## Features

- **Discovery authenticates by default again** (`app/core/config.py`). `KASA_COLLECTOR_TRUST_DISCOVERED_DEVICES` now defaults **True**: a discovered SMART/KLAP device is authenticated with the TP-Link account, the same as an IOT device, so enabling auto-discovery collects it without a manual list. The flag becomes opt-out hardening — set it `False` on a network you do not fully trust and credentials are withheld from any device not in `KASA_COLLECTOR_DEVICE_HOSTS`. The unconditional hardening from the 2026.10.3 audit stays regardless of the flag: credentials are never printed in logs and never sent in the discovery broadcast. (KASACOLLEC-108)

## Refactors

- The one-time "not trusted, opt it in" operator warning is a single `_warn_unlisted` helper, used by both the discovered-SmartDevice path and the credentialed-retry path, so an unlisted device that needs credentials is reported once with an actionable message rather than per cycle. (KASACOLLEC-107)

## Schema / Migrations

No relational database. **No InfluxDB field/tag changes this release.**

## Infra / Ops

**Pre-deploy: none. Post-deploy: none.**

- **Behaviour change — this REVERSES the 2026.10.3 default.** In 2026.10.3, `KASA_COLLECTOR_TRUST_DISCOVERED_DEVICES` defaulted `False` (credentials only to listed devices). It now defaults `True` (discovered devices are authenticated). An operator who wants the stricter gate must now set `KASA_COLLECTOR_TRUST_DISCOVERED_DEVICES=False` explicitly. IOT devices are unaffected either way (they need no credentials).
- **Correction to the 2026.10.3 release notes.** 2026.10.3 stated that setting the trust flag would authenticate every discovered device "as before" — that was not true for SMART/KLAP devices, which dead-ended before the credentialed connection. Fixed in KASACOLLEC-107; the flag now does what 2026.10.3 claimed.
- No guard bumps this release. Coverage floor raised 56 → 68.
- GHCR `:latest` moves to this release (`PUBLIC_LATEST := 1`).

## Fixes

- **The trust/listing path did not authenticate a discovered SMART/KLAP device.** `authenticate_discovered_device` ignores the credentials for a SmartDevice (it only `update()`s the credential-less discovery object), and `_authenticate_device_with_retry` returned at the SmartDevice branch before the credentialed `get_device()` retry. A listed or trusted SMART/KLAP device found by discovery is now reconnected with credentials and collected. (KASACOLLEC-107)
- **An unlisted SMART/KLAP device was logged as needing "newer protocol support".** It is now reported with the actionable "not trusted — add it to `KASA_COLLECTOR_DEVICE_HOSTS` or set `KASA_COLLECTOR_TRUST_DISCOVERED_DEVICES=True`" line, once, and no connection is attempted. (KASACOLLEC-107)
- **A failed SMART probe leaked its connection**, logging `Unclosed client session` / `Unclosed connector` on the event loop each discovery cycle; the device's aiohttp session is now closed on the failure path. (KASACOLLEC-107)
- **The per-cycle "SmartDevice detected … might not be fully supported yet" warning** is now a debug line: a listed/trusted SMART device IS supported via the credentialed retry. (KASACOLLEC-107)
