# 2026.09.1 — 2026-09-20

A device found by discovery once now stays collected — through broadcast silence, through pruning, and through restarts — plus the end-to-end coverage that would have caught why it didn't.

## Issues Closed

- KASACOLLEC-70 — The collector deleted devices it was actively collecting from; three fixes, and the first two were insufficient alone.

## Features

- **The device roster persists.** Every address the collector successfully registers is written to `<OUTPUT_DIR>/known_devices.json` and reloaded at startup, then re-probed by direct unicast. Held only in memory, a restart forgot every device broadcast could not see at that moment. `_check_and_add_emeter_device()` is the single home for remembering — all five registration paths already funnel through it, so the persisted roster cannot drift from the live one.
- **`reclaim_retired_devices()`** — a pruned address is no longer erased. It moves to `retired` and gets a `KasaAPI.get_device()` probe once per discovery round, off the 15-second poll path, so a device that comes back finds its own way in.
- **`KASA_FAKE_DEAF_AFTER`** (emulator) — answer broadcast for N seconds, then rebind UDP from `0.0.0.0` to the container's own address. A socket bound to a unicast address never receives broadcast, so the emulator goes invisible to discovery while still answering a direct query. The mechanism of the live failure, not an approximation of it.

## Schema / Migrations

None. No relational database in this service. Measurements, tags and fields are unchanged.

New state file `<OUTPUT_DIR>/known_devices.json`. It is created automatically, contains only device addresses, and is not required: a missing, corrupt or unwritable roster logs and degrades to discovery-only.

## Fixes

- **The collector deleted devices it was actively collecting from.** `10.10.7.68` wrote its last successful reading at `04:59:10Z` and was deleted as "missing" at `04:59:13Z` — three seconds later. The poller read live data every 15s while discovery, every 300s, deleted anything absent from a broadcast. `discovery_misses` was written and read in one function and nothing in the polling path could reach it, so a device could serve ~60 consecutive successful polls and still be removed. A poll that returns data is direct evidence of presence; an unanswered broadcast is only an inference of absence, and the evidence now wins.
- **Pruning erased the device.** `self.devices.pop(ip)` was the whole mechanism and nothing else recorded that a device had ever been known, so the address went with it and the only route back was the broadcast that had already failed. Pruning exists to stop a departed device eating the poll budget (KASACOLLEC-60); that needs "stop polling", never "forget".
- **Broadcast-invisible devices were unrecoverable across a restart.** Captured on the wire, five devices emitted nothing in response to a broadcast while eleven siblings replied in the same millisecond window — and all five answered unicast instantly with full emeter data. Two of them went silent for twelve hours and started answering again by themselves, nothing changed. Broadcast silence drifts over hours; pruning judged it in fifteen minutes.
- **`.env.example` shipped a contradiction.** It carried `# COMPOSE_PROFILES=bundled` beneath the new default — with every service behind a profile that starts InfluxDB and Grafana and **no collector**. The documented compose snippet also omitted `profiles:` and the `.env.prod` sample omitted `COMPOSE_PROFILES` entirely, which would start nothing.
- The manual-add path and reclaim path both mark a device reachable on registration, so a freshly recovered device cannot be pruned before its first poll lands.

## Notes

**No pre- or post-deploy steps.** No migration, no backfill, no destructive operation.

- **Why this shipped at all: discovery had no end-to-end coverage.** Both fake stacks ran `ENABLE_AUTO_DISCOVERY=False`, on this claim in our own documentation — *"auto-discovery off, since a bridge network can't broadcast"*. It is false. A Docker bridge is a Linux bridge and floods broadcast; a collector on the e2e bridge discovers all four emulators with no configuration. The collector's primary path was untested because it was switched off on an assumption nobody checked. e2e now exercises real discovery.
- **The e2e regression test was vacuous twice before it bit**, both caught by running it against reverted code rather than trusting a green. First it asserted on `SHOW TAG VALUES`, a metadata query over all time: once the device wrote a single point while audible its alias was in the index permanently, and the test passed with *both* halves of the fix reverted. Then, rewritten, it read InfluxDB's empty result as a broken query rather than the zero case, and reported a harness fault instead of the regression.
- **Two diagnoses were wrong and are recorded so nobody re-walks them.** "Discovery is lossy, raise `DISCOVERY_PACKETS`" — disproven: ten packets and an 8s timeout returned the identical set, twice. "An AP is suppressing broadcast" — disproven: `bc_filter_enabled` false on all three SSIDs, no `wlan_overrides` on eight APs, no storm control on any switch port, one flat untagged `/18`.
- Deferred follow-ups, filed not implied: KASACOLLEC-10 (SMART/KLAP emulator — its premise corrected, the discovery half is now covered), KASACOLLEC-37, KASACOLLEC-38, KASACOLLEC-39.
